# Durable passkey application composition

This test-only harness uses the exact same `docs/ServletPasskeyActionsRecipe.java` as the selected volatile host, without another session, grant or authorization implementation. It injects the public RP configured by the unchanged `ServletDurableBackendRecipe.withWebAuthnStore`, the selected `PostgresqlWebAuthnStore`, persistent synthetic sealing/authenticator keys, fixed approved account/namespace and the same reentrant one-host recovery gate. It exercises actual paired Servlet HTTP requests through owned Tomcat and PostgreSQL resources. Never deploy this fixture or its control routes.

`run.py` requires explicit lowercase SHA-256 selections for core, Servlet adapter, normal reference-store JAR, Pyranid and JDBC driver, plus the reviewed Tomcat SHA-512 pin from `../m12-container/runtime.json`. All identities are checked before creating evidence output, Docker resources or listeners. Actual loaded code origins and copied JAR bytes must match. Checker annotations needed by the normal reference JAR's manifest are compile-only; the runtime WAR has only the five selected JARs and the Servlet platform. JUnit and annotation classes must be absent at runtime. The source receipt includes every reference-store main source, schema, inherited application/workflow/backend recipe, the existing test-only worker-clock bridge and new fixture/carrier sources. A separate source/class binding joins the selected normal store artifact to its source packet; filenames alone confer no source credit.

```sh
python3 -B test_artifact_selection.py
python3 -B run.py --tomcat-archive /path/to/reviewed-tomcat.tar.gz \
  --core-jar /path/to/core.jar --core-sha256 CORE_SHA256 \
  --adapter-jar /path/to/servlet.jar --adapter-sha256 ADAPTER_SHA256 \
  --store-jar /path/to/reference-store.jar --store-sha256 STORE_SHA256 \
  --pyranid-jar /path/to/pyranid.jar --pyranid-sha256 PYRANID_SHA256 \
  --driver-jar /path/to/jdbc.jar --driver-sha256 DRIVER_SHA256 \
  --checker-qual-jar /path/to/compile-only-checker-qual.jar \
  --java-home /path/to/jdk --annotations-repository /path/to/maven/repository \
  --scenario main --output /private/tmp/fresh-owned-evidence
```

Use the matching javax/Tomcat9 or jakarta/Tomcat11 inputs and Java17,21,27. PostgreSQL is an already-cached image pinned in the runner; no image or service is downloaded. A random loopback port, private runtime DB role, isolated labeled network/volume/container and private filesystem directory belong only to this run. The runtime role cannot update namespace/epoch/admission/capacity, delete roots, truncate data or delete permanent credential records. All owned processes, instances and database resources are removed in `finally`.

The `main` scenario registers two genuine JCA Ed25519 synthetic credentials, signs in from an anonymous session, completes typed reauthentication, consumes a local action once, and removes a separately selected owned key using another authenticating key. It observes the retained credential tombstone through SQL and the public authoritative credential list. Raw query/header/cookie/body controls cannot mutate the RP. Host admission denies before source/key work. The body cap is enforced after outer-gate metadata checks and before any RP protocol mutation; the gate's PostgreSQL marker reads are explicitly expected.

The SQL oracle observes actual full storage keys, kinds, versions, sealed-form hashes, exact expiry projections and **all256** entry quotas. It derives each bucket from the storage key with separate SHA-256 logic and compares exact usage with row counts. Refusal checks compare all data/version/quota observations. Sequence allocation is recorded separately because an attempted rolled-back transaction can leave PostgreSQL sequence gaps; that is not a committed credential or quota effect.

A normal Tomcat/JVM restart retains the same private synthetic keys, saved synthetic-authenticator counter files and PostgreSQL credentials, while losing volatile browser sessions, pending actions and local grants. A new anonymous session must complete a real signed assertion; an old pending action cannot transfer into it. A real PostgreSQL-container restart preserves the observed data/all256 quotas. The recipe's session store remains volatile; these are not durable-session or high-availability claims.

Fresh-process scenarios `unknown-before`, `unknown-after` and `known-after` stop after the fault outcome and destroy the owned environment. Their JDBC proxy observes one actual mutation commit entry: it throws before committing, commits then throws a lost acknowledgement, or preserves the successful commit and makes final authority unavailable. SQL ground truth distinguishes no committed row effect, an applied UNKNOWN batch, and a known committed effect with withheld authority. All three withhold local grants, close application admission, and make no automatic retry, response/status rescue or reopen. The latter is not labeled UNKNOWN. A restart of a closed uncertain controller is not used as a recovery mechanism.

The worker and data authority are **separately scripted** through explicit fixed channels at the chosen fixture timestamp; maximum UTC error is zero as a fixture declaration. `worker-forward` moves only the worker by six seconds and requires refusal without using the worker or database wall clock as authority. The inherited `WebAuthnFixtureWorker` is a test-only package bridge to the existing package-private clock hook, not a new public API or a qualified time service. No UTC/rate/ownership qualification follows from these values.

The fixture's recovery gate derives the existing reference example's one-host external-file barrier: a shared OS file lock spans the app/RP operation, a bounded current check compares the startup external epoch/sealing-key digest with its separate DB marker, and nested permits retain that same lock. An actual post-commit pause outside the PostgreSQL transaction proves an exclusive controller lock refuses while genuine core work is still held. After the operation drains, the controller takes that exclusive lock and the reference store's exact exclusive admission lock before changing its recovery metadata and marker. The retained old host then refuses both its preexisting local grant and new RP work without mutation. This is a bounded local barrier/correlated metadata rehearsal, not a durable witness across a fleet, restore protocol or deployment profile.

`calibrate.py` starts a green native control and three private new-fixture plants: dropping the actual lost acknowledgement, secretly committing the declared no-effect fault, and ignoring both external/DB epoch comparisons. Each must fail its named application or independent SQL assertion after successful preparation and must clean owned resources. These controls calibrate this fixture/oracle and selected boundary, not all PostgreSQL behavior or a full mutation score.

The connector runs plaintext loopback with trusted synthetic `scheme=https secure=true`; it is not TLS/browser evidence. Receipts retain only safe counters, synthetic key fingerprints, source/artifact identities, hashes, named assertions, independent SQL observations and cleanup. This component does not qualify physical authenticators, hosted services, cross-host recovery, a customer deployment, full profileC, formal tools or the final merged release candidate.
