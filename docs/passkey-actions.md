# Typed passkey actions application

`ServletPasskeyActionsRecipe.java` is a complete, deliberately small application around the public WebAuthn APIs. It has one startup-approved account, a separate operator access key, volatile browser sessions and two selected actions: a local sensitive-action counter and removal of one selected credential. It demonstrates application authorization after a genuine ceremony; it is not a general session or account-management product.

Inject a fixed HTTPS origin, exact RP ID, account handle, credential namespace, `Clock`, `WebAuthnRelyingParty` and the **same reentrant** `WebAuthnRecoveryGate` used by that RP. Configure the RP's selected authoritative store and sealing keys at startup. The constructor validates the explicit namespace/RP/account tuple; it does not infer application policy from a proof. The injected RP must use the same origin/account scope and a response-body limit no larger than 65,536 bytes. Never obtain this configuration from HTTP headers, a token, JSON or an authenticator response.

The host must supply trusted TLS and fixed routing. The application requires exact Host, HTTPS scheme/security state and Origin, rejects query strings (including a bare query delimiter), forwarded headers, bearer authentication and ambiguous critical headers/cookies, and checks raw-body completion. A reverse proxy must preserve the selected carrier semantics and establish its scheme/security state through trusted configuration. Declaring a request secure is not evidence of a TLS handshake or preservation of physical wire headers.

Mount this servlet at `/passkeys/*`. GET `/session` reports the current local session without allocating one. POST `/session` with an empty body and exact Origin starts an anonymous session and returns its CSRF token. `/access-login` requires that anonymous session, CSRF and the separate `X-Demo-Access-Key` to rotate into the single approved account. This operator bootstrap is an explicit example assumption, not a password or passkey authentication claim.

Registration `/register/start` and `/register/finish` requires the current authenticated session, CSRF and operator key. `/sign-in/start` and `/sign-in/finish` perform real general sign-in from an anonymous session; only a scoped `SIGN_IN` proof for the approved account rotates the session. `/credentials/list` uses the authoritative RP list for that account. `/logout` rotates to a new anonymous session; an already-held old session object cannot publish new authority.

For `/reauth/start`, save the core's prepared ceremony ID in the current session's pending **object** with fixed purpose `demo-sensitive-action`. `/reauth/finish` accepts only `WebAuthnReauthenticationResult.Succeeded.getReauthentication()`, then compares current session/account, namespace, RP, purpose, ceremony ID and exact pending-object identity. The proof's credential ID identifies the authenticating key; it is not a requested removal target. The five public result leaves are handled without constructing, converting or serializing proofs.

A successful finish installs one local action grant. POST `/sensitive` takes and clears that slot before checking the selected action, target and expiry. Concurrent requests have at most one winner. The grant expires strictly before its 60-second deadline and the session's original 10-minute deadline. This Servlet profile additionally caps both lifetimes using bounded relative monotonic durations; the selected Soklet example retains its stated wall-clock profile. The extra cap is a local policy difference, not a claim that the implementations have identical timing policy.

Credential self-removal uses `/credentials/self-remove/start`, `/credentials/self-remove/finish` and `/credentials/self-remove`, fixed purpose `demo-remove-passkey` and canonical `X-Credential-Id`. Begin confirms the selected target belongs to the account, then stores it server-side. The authenticating key can be another owned key. A wrong action or target consumes the slot and denies the action. The selected removal makes exactly one public RP call after consuming the grant; no refund or retry follows an uncertain result. `/credentials/remove` remains a separate operator-key path, not a fallback from failed reauthentication.

The application admits at most eight operations before RP/store work. It retains at most 64 sessions, one pending action and one grant per session; live sessions are never evicted to admit another. It checks the original operation deadline and current session after callbacks and after successfully closing the recovery permit, before writing a response. No RP, store or gate callback runs under the session-store monitor. A late callback after logout or pending replacement cannot grant authority.

A response frame owns only its exact newly-created grant. A final eligibility refusal, close failure or observed synchronous writer failure burns that reference without reading a clock or calling any collaborator. An old refusal cannot clear a newer grant or one owned by another application instance. Runtime publication failures do not cause a second application write attempt. A successful handoff to the Servlet container does not prove peer receipt. An action or core mutation that already happened remains factual when its response is withheld.

`Indeterminate` or `ReconciliationRequired` closes local application admission. This application has no automatic retry, status/read rescue, reset or reopen endpoint. A trusted operator must reconcile the selected store/controller before replacing this local host. A JVM restart alone is not a recovery protocol. The volatile session/grant state has no durable, fleet or restart-continuity claim.

See `verification/passkey-actions-container/README.md` for actual synthetic signed-credential, carrier, concurrency, fault and private calibration checks. Physical authenticators, owner deployment, real TLS/browser composition, durable store composition, the final merged candidate and package qualification are separate gates.
