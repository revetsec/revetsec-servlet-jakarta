# Restrictive SCIM directory application

`ServletScimDirectoryRecipe.java` is the S4 application host for the paired Servlet adapters. Register one long-lived instance at `/scim/*` in the root context. It uses the public `ServletBearer`, `ServletScim`, `JwtAccessTokenValidator`, `RemoteJwksSource`, SCIM parser/evaluator/response APIs and `PasswordHasher`; it does not add a core API. Select the matching namespace source and adapter. The two source copies differ only in their Servlet namespace imports.

This is a deliberately narrow, volatile directory. It implements Users and Groups CRUD, per-type GET lists and POST `.search`, discovery, exact conditional mutations, requested and effective field policy, and credential preparation. It is suitable as a reviewable application integration example. It does not provide a durable directory, shared database transactions, bulk provisioning, arbitrary SCIM schemas, cursor pagination, arbitrary filter operators or a complete Unicode matching policy.

## Trusted startup and principal policy

Construct `Configuration` with a fixed root HTTPS application origin, exact issuer, audience, HTTPS JWKS URI and at most eight registered tenant identifiers. `createJwt` fixes RS256, the issuer/audience, `tenant` and `scope` claims, zero token clock skew, an 8,192-character token bound, one-second remote calls, a three-second validation deadline, fresh key policy and eight keys. No unverified token field selects an issuer, key endpoint, algorithm or tenant policy. Register trusted `Identity(issuer, subject, clientId)` records and current `Principal` values in one `Directory`. A signed role claim does not grant a role. The token tenant, trusted principal tenant and fixed route tenant must all match before directory work.

A PROVISIONER may create/delete and change the declared User and Group fields; primary credential changes additionally require the current trusted `credentialChangesAllowed` flag. A READER only reads. A SELF principal only sees its own active User and may PATCH its declared display/name fields. SELF does not gain password reset. Collection counts and pages are scoped to the current tenant and owner before filtering, sorting or response projection. The exact current principal record, including its generation, and the exact immutable directory snapshot are compared again before any data or mutation response is released. An intervening policy or state change refuses; it does not silently rebase, retry or publish a prepared response.

`Admission.allow` receives the direct peer and remaining monotonic budget. Supply an application-specific bounded admission policy. Do not derive trusted principals, role, tenant, owner, credential permission or generation from request JSON, query parameters, forwarded headers or an unverified token. The directory is intentionally populated from trusted application startup records; an application with a live policy service must replace it with its own exact transaction and qualification rather than adding an asynchronous policy callback inside the final lock.

## Request and directory bounds

The recipe requires secure fixed-origin requests and the exact root Servlet mapping/URI. It refuses cookie authentication, query bearer tokens (including encoded parameter names), duplicate bearer carriers, hostile or duplicate Origin, and GET/DELETE request bodies. It reads original Servlet header enumerations and uses the adapter's bounded body reader, content-type, query, conditional-header and response helpers. It does not use `getParameter`, reconstructed query strings or decoded path aliases for security decisions. The fixture's HTTP connector `secure=true` flag is a synthetic carrier input, not proof of HTTPS.

The host has eight shared permits before admission, token/key validation, protected reads or credential work. A ninth operation refuses without evicting accepted work. It has an eight-second monotonic host budget and rechecks interruption, wall-clock rollback and exact token expiry after collaborators and inside the final transaction. Collaborators must honor their supplied remaining duration; this synchronous example cannot forcibly cancel an arbitrary blocking application callback. Configure real request/response timeouts and bounded threads at the server/edge too.

Each tenant holds at most 64 total User/Group rows and 262,144 charged bytes. Registered tenants are capped at eight and principal registrations at 128. The row cap, ASCII 256-character scalar field limits, same-tenant ID-only Group members (at most 32), 16-KiB bodies, 16 PATCH operations, 2-KiB raw queries/eight parameters, bounded JSON/filter/work/response limits, 20-result pages and bounded scalar sort comparisons all apply before publication. Capacity refusal preserves resources, credentials, IDs, versions and byte charges. DELETE reclaims row and byte admission. There is no admission eviction or background allocation on read.

The application executes only the core-approved filter AST through `ScimFilterEvaluator`; it never turns a raw filter into a backend expression. EQ/NE/presence and bounded AND/OR/NOT are approved on the documented scalar fields. Sort fields are fixed scalars with stable ID ties. User ID, external ID and Group member value matching remains exact where defined; this host's other supported string matching is ASCII. Unsupported matching fails closed. Non-ASCII directory strings, nested filters outside this profile and cursor requests are not accepted as substitutes for a complete Unicode/backend query implementation.

## Credentials, versions and outcomes

The registered built-in User `password` is handled as a credential only when its actual schema definition is WRITE_ONLY and NEVER returned. A distinct fixed extension attribute named `password` is an ordinary public directory label, is preserved and does not invoke the KDF; never place a secret there. The tests exercise this schema distinction. A caller-supplied `PasswordHasher` must use a bounded shared work gate and current application cost policy. The fixture's Argon2id parameters are test settings, not a universal customer strength policy.

`CredentialPolicy.accepts` is a bounded read-only check of a borrowed `char[]`; it must not retain or mutate the array. The application clears that array in `finally`, including refusal and cancellation. Parsed JSON and Servlet input necessarily include immutable strings/bytes; this recipe cannot promise erasure of every in-memory copy. The primary password is stripped from the stored resource and retained only as the prepared hash. Null/removal is refused; omitted write-only password on PUT preserves the old credential. An identical submitted credential is verified and leaves a true no-op version unchanged.

Parsing, field policy, integrity checks, KDF/callbacks and bounded response preparation all happen outside the directory/version lock. Under one short lock, the host checks exact current policy, exact snapshot/version and exact token/host deadline, then atomically replaces the resource, credential, sequence, version and byte accounting. Mutations require one exact current `If-Match`; missing, wildcard, duplicated or stale values refuse. Same-version concurrent writers produce one publication. Group member additions and User deletion cannot leave a dangling same-tenant reference. Requested paths are checked even when the operation is a no-op. The separate effective-path policy permits only implicit Group member metadata removal reported by the core after an authorized ID change; it does not permit a caller to supply foreign `$ref`, `display` or `type` metadata.

Only a CONFIRMED publication emits success. A known unavailable operation has no state effect. The fixture's deliberately applied UNKNOWN operation returns 503 and is never automatically replayed or rescued by a read. Required unique per-tenant/type `externalId` gives the caller an explicit reconciliation query for an uncertain create; it is not an instruction to retry automatically. A transport failure while writing an already committed response can also leave the caller uncertain. Reconcile the intended object and current version explicitly. Do not infer that withholding a response rolled back a confirmed mutation.

## Qualification and deployment limits

The paired `verification/scim-directory-container` harness runs actual signed access tokens/JWKS, actual core SCIM parsing/evaluation and PasswordHasher, current-policy/expiry/cancellation injections, raw HTTP carriers, actual concurrent requests and the real pinned Tomcat runtime. It uses owned disposable loopback resources, an unlogged fixture credential and a separate fixture class; no fixture controls belong in production. Receipts record exact source, core/adapter and runtime hashes. Fresh fault processes distinguish an actual failed key endpoint from refresh admission holdback. Private planted defects must fail at their named assertions after a green control.

The selected qualification core is historical component `923c6607159e0f159c8c09660910749db51d4bac482454700d2ba0b6db548bf5`; receipts do not certify a later merged JAR. Strict release-17 source compilation, attributed explicit nullability and JDK17/21/27 container runs establish the recorded local subset only. Keep final merged-artifact requalification, real trusted HTTPS/proxy/raw physical-header preservation, customer identity/credential policy, production routing/timeouts, durable/shared store semantics, browser/CORS integration and full formal M12/SCIM tool/profile gates open. A Servlet container or edge that normalizes away a relevant ambiguous physical carrier must reject it at the qualified edge; an application declaration is not evidence that the physical carrier survived.
